# 1. 本卷的学习目标：从“会用”到“能读源码”

如果你计划长期使用 Freqtrade，真正重要的能力不是记住几十个 callback 名称，而是回答下面这些问题：

- 这次 `enter_long = 1` 最终为什么没有成交？
- 一个 DataFrame 是谁创建的？谁缓存的？什么时候刷新？
- 为什么 `custom_stoploss()` 可能被重复调用？
- 为什么 `backtest` 和 `dry_run` 对同一根 K 线的结果可能不同？
- 一个订单已经在交易所成交，但本地数据库为什么还没变？
- FreqUI 显示的数据是从 Strategy 来的，还是从 Trade / RPC 来的？
- 为什么改了 Strategy 文件，bot 必须重启？
- 多 bot 使用同一策略文件时，运行时状态究竟是共享的还是隔离的？
- `self.dp`、`self.wallets`、`self.config` 到底是谁注入的？
- 如果你要增加“组合级日内亏损上限”，应该改 Strategy、Protection、Wallets，还是 Bot？

理解这些问题，才算真正脱离黑盒。

一个非常重要的原则是：

> **Strategy 决定“想做什么”；Bot 决定“什么时候检查”；Risk / Protection 决定“允许不允许”；Exchange 决定“怎样下到交易所”；Persistence 决定“系统是否记得发生过什么”；RPC/UI 决定“你怎样观察和控制它”。**

# 2. Freqtrade 源码树：先建立地图

当前仓库的源码组织可以粗略理解为：

```text
freqtrade/
├── commands/                 # CLI 命令入口与命令编排
├── configuration/            # 配置读取、校验、覆盖
├── data/                     # 历史数据、转换、DataProvider、分析
├── edge/                     # Edge 相关功能
├── exchange/                 # 交易所抽象、CCXT、WebSocket、精度、报价
├── freqtradebot.py           # 主交易引擎
├── hyperopt/                 # Hyperopt 参数搜索
├── optimize/                 # Backtesting / Hyperopt 运行层
├── persistence/              # Trade、Order、DB、custom_data
├── plugins/                  # Pairlist、Protection 等插件化组件
├── rpc/                      # Telegram、REST API、WebSocket、RPC
├── strategy/                 # Strategy Interface、Decorator、Resolver、wrapper
├── templates/                # 策略与配置模板
├── wallets.py                # 资金与余额抽象
├── worker.py                 # Worker 生命周期
├── ftbot.py                  # 部分启动/兼容入口
└── util/                     # 通用工具、缓存、时间、迁移等
```

从“主交易路径”看，最值得先读的是：

```text
worker.py
   ↓
freqtradebot.py
   ↓
resolvers/strategy_resolver.py
   ↓
strategy/interface.py
strategy/strategy_wrapper.py
   ↓
data/dataprovider.py
   ↓
exchange/exchange.py
   ↓
persistence/trade_model.py
   ↓
rpc/*
```

然后再去读：

```text
plugins/pairlistmanager.py
plugins/protectionmanager.py
wallets.py
optimize/backtesting.py
hyperopt/*
configuration/*
commands/*
```

你可以把第一组理解成“主干”，第二组理解成“支撑系统”。

官方仓库当前的核心文件仍然维持这一职责划分；例如 `FreqtradeBot` 明确引用了 DataProvider、PairListManager、ProtectionManager、StrategyResolver、RPCManager、Wallets、Trade、Order 等组件。 [官方源码](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/freqtradebot.py)

# 3. Python 入口、Worker 与主生命周期

## 3.1 从 CLI 开始，而不是从 Strategy 开始

很多新用户会直接打开 `SampleStrategy.py`。对于源码学习，建议反过来：先从命令入口开始。

典型命令：

```bash
freqtrade trade -c user_data/config.json
```

这个命令背后的重要问题不是“执行了什么 shell 命令”，而是：

1. CLI 如何把参数解析进配置对象？
2. 配置如何合并命令行参数、config 文件和默认值？
3. 谁决定进入 `trade` 模式？
4. 谁实例化 Worker？
5. Worker 谁实例化？
6. Worker 谁创建 `FreqtradeBot`？

官方当前使用 Python 3.11+，源码安装文档也明确区分 `stable` 与 `develop` 分支。 [安装文档](https://github.com/freqtrade/freqtrade/blob/develop/docs/installation.md)

## 3.2 Worker 的职责

不要把 Worker 理解成“策略执行器”。更准确的理解是：

> Worker 是进程级的生命周期控制器；`FreqtradeBot` 才是交易业务核心。

概念结构：

```text
Operating System
      │
      ▼
   process
      │
      ▼
    Worker
      │
      ├── startup
      ├── heartbeat / loop
      ├── throttle
      ├── error handling
      ├── graceful shutdown
      │
      ▼
 FreqtradeBot
```

这意味着一个很重要的工程事实：

**如果你想增加“交易逻辑”，通常应该找 `FreqtradeBot` / Strategy / plugins；如果你想改变“进程如何生存”，才考虑 Worker。**

## 3.3 为什么主循环不能直接写成无限快的 `while True`

真实交易系统必须控制：

- 请求频率
- API 限流
- 交易所 DDoS protection
- CPU 占用
- candle 刷新节奏
- 未成交订单检查频率
- 状态广播频率
- UI 更新负载

因此系统会存在 throttle / scheduling / cache 等机制。

错误思路：

```python
while True:
    check_signal()
    submit_order()
```

更接近实盘框架的思路：

```text
loop tick
   ↓
处理应该周期性检查的事务
   ↓
检查当前市场状态
   ↓
维护已有交易
   ↓
在满足条件时分析新信号
   ↓
触发订单生命周期
   ↓
持久化
   ↓
RPC/UI 通知
   ↓
throttle / sleep
```

# 4. `FreqtradeBot`：真正的运行时核心

当前源码中，`freqtradebot.py` 自身已经是一个非常大的核心模块。源码顶部会直接引用：

```python
from freqtrade.data.dataprovider import DataProvider
from freqtrade.plugins.pairlistmanager import PairListManager
from freqtrade.plugins.protectionmanager import ProtectionManager
from freqtrade.resolvers import ExchangeResolver, StrategyResolver
from freqtrade.rpc import RPCManager
from freqtrade.persistence import Order, PairLocks, Trade, init_db
from freqtrade.wallets import Wallets
```

这几行 import 本身就非常有价值：

> 它告诉你 `FreqtradeBot` 不是“策略调用器”，而是一个把交易系统各种组件装配起来的 orchestration layer。

官方当前源码可从这里开始读： [freqtradebot.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/freqtradebot.py)

## 4.1 Bot 初始化的概念顺序

不要执着于某个版本某一行代码的绝对顺序，先理解对象拓扑：

```text
Config
  │
  ├── Exchange
  ├── Strategy
  ├── Wallets
  ├── PairListManager
  ├── ProtectionManager
  ├── DataProvider
  ├── RPCManager
  └── Persistence / DB
```

这里最关键的关系是：

```text
Strategy
  │
  ├── self.config
  ├── self.dp
  ├── self.wallets
  └── 与 Trade / Bot 间接交互
```

所以 Strategy 本身并不是“孤立纯函数”。它在 live 环境中是一个被 runtime 注入依赖的对象。

## 4.2 为什么这个设计重要

假设你在 Strategy 里写：

```python
self.dp.get_pair_dataframe(pair, "1h")
```

你看到的只是一个简单函数调用。

但从架构角度，它其实穿过：

```text
Strategy
  ↓
DataProvider
  ↓
Data cache / analyzed data / historical provider
  ↓
Exchange / History / Producer
```

所以你不能把 `self.dp` 当成“一个 DataFrame 变量”。

# 5. StrategyResolver：策略究竟是怎样被加载的

## 5.1 为什么 Freqtrade 可以只在配置里写类名

配置通常会写：

```json
{
  "strategy": "MyStrategy"
}
```

然后运行：

```bash
freqtrade trade -c config.json
```

这里存在一个隐藏步骤：

```text
config["strategy"]
        ↓
StrategyResolver
        ↓
扫描 strategy 搜索路径
        ↓
import Python module
        ↓
寻找符合条件的 class
        ↓
实例化 IStrategy 子类
        ↓
注入运行时属性
```

这就是为什么你可以把：

```text
user_data/strategies/MyStrategy.py
```

放进策略目录，然后通过类名直接加载。

## 5.2 `list-strategies` 为什么很有用

官方提供：

```bash
freqtrade list-strategies
```

它的作用不仅是“列出策略”，还是一个非常好的加载诊断工具。

如果出现：

```text
LOAD FAILED
```

你应该立刻怀疑：

- Python import 错误
- 缺失依赖
- 类名不匹配
- 语法错误
- 指标库没有装好
- import 的本地模块路径错误

官方当前文档也明确说明 `list-strategies` 可以显示 `LOAD FAILED` 和 `DUPLICATE NAME`。 [官方 utils](https://github.com/freqtrade/freqtrade/blob/develop/docs/utils.md)

## 5.3 一个非常有用的开发流程

每次改 Strategy 后，先：

```bash
freqtrade list-strategies
```

再运行：

```bash
freqtrade trade --strategy MyStrategy -c user_data/config.json --dry-run
```

不要一上来直接重启生产 bot。

# 6. `IStrategy`：策略对象到底拥有了什么

当前源码中 `strategy/interface.py` 是策略行为的根接口。它定义了大量默认属性、生命周期 hooks、分析逻辑和交易条件检查。 [strategy/interface.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/strategy/interface.py)

## 6.1 Strategy 可以粗略分成五类能力

```text
A. 静态策略属性
   timeframe / minimal_roi / stoploss / trailing / can_short ...

B. 向量化分析
   populate_indicators
   populate_entry_trend
   populate_exit_trend

C. 运行时交易 callbacks
   custom_exit
   custom_stoploss
   custom_roi
   custom_stake_amount
   confirm_trade_entry
   confirm_trade_exit
   adjust_trade_position

D. 生命周期 hooks
   bot_start
   bot_loop_start
   bot_stop
   order_filled

E. 数据与运行时依赖
   self.dp
   self.wallets
   self.config
```

## 6.2 Strategy 不是“一个函数”，而是一台状态机

从工程角度看，一个 Strategy object 有：

```text
静态配置
   +
运行时依赖
   +
缓存/内部状态
   +
参数
   +
DataFrame 分析逻辑
   +
Trade callback
```

因此你必须明确区分：

### “每根 K 线可重算”的状态

例如：

```python
dataframe["atr"] = ta.ATR(dataframe, timeperiod=14)
```

### “交易生命周期状态”

例如：

```python
trade.user_data
trade.open_date_utc
trade.max_rate
trade.stop_loss
```

### “策略实例状态”

例如：

```python
self.cached_regime
self.some_runtime_cache
```

三者不能混为一谈。

# 7. `strategy_wrapper`：为什么 callback 出错时日志长成这样

Freqtrade 的 callback 并不是直接裸奔执行。运行时会通过 wrapper / safe wrapper 一类机制捕捉异常、添加上下文并控制错误传播。

这带来一个非常重要的 Debug 技巧：

看到类似：

```text
Unexpected error ... calling <bound method ...>
```

不要只看最后一行。

要向上追：

```text
strategy_wrapper
    ↓
具体 strategy callback
    ↓
你的业务函数
```

这能解释为什么很多 Stack Trace 最后会同时出现：

```text
freqtrade.strategy.strategy_wrapper
freqtrade.strategy.interface
你的 Strategy 文件
```

其中：

- wrapper 是“护栏”
- interface 是“策略调度层”
- 你的文件才是“业务逻辑”

# 8. `DataProvider`：数据是怎样流入 Strategy 的

官方当前的 `DataProvider` 不只是“返回 DataFrame”这么简单。源码明确包含：

- cache
- exchange
- pairlists
- RPC
- backtesting dataframe
- producer dataframe
- ticker / orderbook / market
- 历史数据读取

[官方 DataProvider 源码](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/data/dataprovider.py)

## 8.1 DataProvider 的核心思想

```text
                     ┌──────────────┐
                     │   Strategy   │
                     └──────┬───────┘
                            │
                         self.dp
                            │
              ┌─────────────┼─────────────┐
              │             │             │
              ▼             ▼             ▼
        pair dataframe   ticker      orderbook
              │
              ▼
         informative data
              │
              ▼
        producer / cache
```

## 8.2 为什么不能把 `dp.get_pair_dataframe()` 理解成“现查交易所”

这是最重要的认知之一：

> DataProvider 是数据访问抽象层，而不是“每调用一次就发 HTTP 请求”的快捷函数。

系统为了性能会依赖缓存、历史数据处理和运行模式差异。

如果你在 callback 里写：

```python
df = self.dp.get_pair_dataframe(pair, self.timeframe)
```

不能推出：

```text
callback -> HTTP request -> exchange -> response
```

真实情况可能是：

```text
callback
   ↓
DataProvider
   ↓
cache / analyzed dataframe / local history / exchange
```

## 8.3 DataProvider 与不同运行模式

同一个 `self.dp` 接口，在：

- live
- dry-run
- backtesting
- webserver
- producer/consumer

中可能拥有完全不同的数据来源和生命周期。

这就是抽象的价值：Strategy 不需要知道“数据来自哪里”，但源码阅读者必须知道。

# 9. Exchange：Freqtrade 如何穿过 CCXT 与交易所

当前 Exchange 层本身非常大，它负责：

- 市场 metadata
- OHLCV
- ticker
- orderbook
- balance
- create order
- cancel order
- order status
- leverage / position
- precision
- fee
- rate limit
- retries
- WebSocket / async support
- 交易所差异适配

当前源码可从 `freqtrade/exchange/exchange.py` 开始。 [Exchange 源码](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/exchange/exchange.py)

## 9.1 CCXT 不是 Freqtrade 本身

理解三层：

```text
Strategy / Bot
      ↓
Freqtrade Exchange abstraction
      ↓
CCXT / CCXT Pro
      ↓
Binance / Bybit / OKX / Kraken ...
```

因此：

```python
exchange.create_order(...)
```

不等于直接调用某个交易所原生 API，而是在 Freqtrade 的统一接口之下继续经过 CCXT 及交易所适配逻辑。

## 9.2 为什么不同交易所仍然会有坑

“Freqtrade 支持这个交易所”并不意味着：

```text
所有 feature == 所有交易所完全一致
```

常见差异：

- precision
- min amount
- min notional
- stop order 类型
- futures position mode
- leverage tiers
- orderbook 支持
- WebSocket 支持
- order flags
- funding data

所以策略如果直接假设交易所行为完全一致，迁移风险很大。

## 9.3 Precision 是一个常见黑盒

例如你计算：

```python
stake = 123.456789
```

最终真实下单量不会一定精确等于这个数字。

因为需要经过：

```text
strategy stake
   ↓
wallet constraint
   ↓
market precision
   ↓
contract precision
   ↓
min amount / min notional
   ↓
rounding
   ↓
exchange order
```

这就是为什么“我策略里计算出来的 stake”与“交易所实际成交量”之间可能存在差异。

# 10. Pairlist、Protection、Wallets：进场前的三个“闸门”

很多策略作者看到：

```python
dataframe.loc[cond, "enter_long"] = 1
```

就认为“下一步一定会开仓”。

这是错误的。

你可以把真正的入场判断画成：

```text
Signal
  │
  ▼
Pair 可交易？
  │ yes
  ▼
Pair 是否被锁？
  │ yes
  ▼
Protection 是否允许？
  │ yes
  ▼
Max open trades 是否已满？
  │ yes
  ▼
Wallet 是否有钱？
  │ yes
  ▼
Stake 是否合法？
  │ yes
  ▼
Entry confirmation
  │ yes
  ▼
Exchange
```

## 10.1 Pairlist

Pairlist 解决：

> “今天哪些市场属于我的 trading universe？”

它不是策略信号。

一个 pair 即使：

```text
enter_long = 1
```

如果不在最终 whitelist 内，也没有机会进入后续交易路径。

## 10.2 Protection

Protection 是一个非常值得你单独研究的层。

它解决：

> “即使策略有信号，现在是不是也不应该继续做？”

例如：

- stoploss guard
- cooldown
- max drawdown
- low profit / low winrate 类限制

这是“策略逻辑”和“账户级风控”之间的桥梁。

## 10.3 Wallets

Wallets 决定：

> “你现在到底有多少钱可以拿来交易？”

这意味着策略里面的：

```python
return 100
```

也不代表真的下 100 stake。

资金约束仍然存在。

# 11. Trade / Order：数据库中的交易状态机

当前 Freqtrade 使用 SQLAlchemy 持久化 Trade / Order。官方 `trade_model.py` 中明确说明：一个 Trade 可以关联多个 Order，而一个 Order 只关联一个 Trade。 [trade_model.py](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/persistence/trade_model.py)

## 11.1 为什么 Trade != Order

这是理解 Freqtrade 的关键。

```text
Trade
  ├── Entry Order 1
  ├── Entry Order 2
  ├── Adjustment Order
  ├── Exit Order 1
  └── Exit Order 2
```

一个策略层面上的“交易”，可能经历多个交易所订单。

例如：

```text
开仓
↓
第一次挂单
↓
部分成交
↓
补充订单
↓
加仓
↓
部分退出
↓
最终退出
```

如果你只看一个 `Order`，无法描述完整交易生命周期。

## 11.2 Trade 保存了什么

典型信息包括：

```text
pair
strategy
enter_tag
exit_reason
timeframe
open_date
close_date
open_rate
close_rate
stake_amount
amount
stop_loss
initial_stop_loss
max_rate
min_rate
profit
fees
trading_mode
```

因此 Trade 更像一个“交易会计对象 + 生命周期状态容器”。

## 11.3 为什么数据库是实盘系统的一部分，而不是日志

日志告诉你：

```text
某个时刻发生了什么
```

数据库告诉你：

```text
系统现在认为世界处于什么状态
```

这两个概念完全不同。

实盘 bot 重启后必须能回答：

- 哪些 Trade 还开着？
- 哪些 Order 还挂着？
- 哪些止损状态存在？
- 账户资金是多少？
- 哪些交易已经完成？

这就是 Persistence 的意义。

# 12. 一个入场信号从 DataFrame 走到交易所的完整调用链

现在把整个系统串起来。

假设：

```python
dataframe.loc[long_condition, "enter_long"] = 1
```

你应该在脑中形成下面的调用链：

```text
OHLCV
  ↓

  ↓
Strategy.analyze...
  ↓
populate_indicators()
  ↓
populate_entry_trend()
  ↓
enter_long
  ↓
Bot 获取当前 signal
  ↓
检查 Pair 状态
  ↓
检查 Pair lock / Protection
  ↓
检查 open trade 数量
  ↓
检查 wallet / stake
  ↓
确定 entry side
  ↓
计算 amount / rate
  ↓
confirm_trade_entry()
  ↓
create order
  ↓
Exchange
  ↓
CCXT
  ↓
交易所
  ↓
返回 order id
  ↓
创建 / 更新 Trade + Order
  ↓

  ↓
UI / Telegram / Webhook
```

## 12.1 关键思想：signal 是“意图”，不是“订单”

这是策略设计里非常容易犯的错误。

错误认知：

```text
enter_long = 1
        ==
开仓成功
```

正确认知：

```text

```

中间还有完整的风控、资金、执行、撮合链路。

这也是为什么策略调优时，不能只看 signal count。

# 13. 一个退出信号从持仓走到平仓的完整调用链

退出比入场更复杂，因为存在多个独立退出来源：

```text
Entry strategy signal
Custom exit
ROI
Stoploss
Trailing stop
Position adjustment
Exchange stop order
Timeout
Manual RPC command
```

概念上：

```text
Open Trade
    │
    ├── exit signal?
    ├── custom_exit?
    ├── ROI reached?
    ├── stoploss reached?
    ├── trailing condition?
    ├── timeout?
    ├── user/manual exit?
    └── position adjustment?
          │
          ▼
     exit decision
          │
          ▼
 confirm_trade_exit()
          │
          ▼
 Exchange
          │
          ▼
 Order
          │
          ▼
 Trade closed / updated
```

## 13.1 `custom_exit` 不等于“立即平仓函数”

它本质上是：

> 一个策略层可编程的 exit decision hook。

如果你的逻辑是：

```python
if current_profit > 0.05:
    return "take_profit"
```

策略表达的是：

```text
“我认为现在可以退出。”
```

真正的成交仍然经历后面的执行流程。

## 13.2 为什么退出理由非常重要

生产系统不要只记录：

```text
profit = 2.1%
```

更有价值的是：

```text
profit = 2.1%
exit_reason = custom_exit
exit_tag = trend_failure
```

因为长期优化的本质是研究：

> **什么类型的进入，最终由什么类型的退出完成。**

# 14. `custom_stoploss`、`custom_exit`、`adjust_trade_position` 的真实运行模型

## 14.1 不要把 callback 当普通函数

普通函数：

```python
result = f(input)
```

callback：

```text
runtime decides when to call you
runtime decides what context you receive
runtime interprets your return value
runtime determines whether your return value is actionable
```

这就是 callback 的本质。

## 14.2 `custom_stoploss`

它最容易被误用成：

```python
return -0.03
```

但真正应该关注的是：

- 当前 profit
- current rate
- current time
- trade state
- 是否可以移动止损
- 交易所 stoploss 支持
- 是否会频繁修改订单

如果把 stoploss 每一轮都设计成“重算一个完全不同的位置”，可能导致：

```text
频繁修改
↓
交易所 API 压力
↓
费用 / 延迟 / 状态竞争
```

## 14.3 `adjust_trade_position`

这是高级功能，也是最容易把系统搞复杂的 callback 之一。

例如：

```python
return 100.0, "add_on_pullback"
```

你的意图不是“重新开一单独立交易”，而是：

> 对现有 Trade 调整仓位。

这会导致 Trade 与 Order 关系更加重要。

推荐首先建立一个状态模型：

```text
Trade
  ├── original entry
  ├── adjustment #1
  ├── adjustment #2
  ├── partial exit
  └── final exit
```

然后再考虑策略逻辑。

## 14.4 一个实用原则

在没有充分理解 Trade/Order 状态机前，不建议同时启用：

```text
adjust_trade_position
+
custom_stoploss
+
custom_exit
+
trailing
+
多个 exit signal
```

否则你很难判断“到底是谁让仓位发生了变化”。

# 15. `RPC → REST API → WebSocket → FreqUI` 控制面

很多人把 FreqUI 理解成“交易机器人网页”。更准确的理解是：

> FreqUI 是一个控制面客户端，而不是交易逻辑本身。

概念架构：

```text
                    ┌───────────────┐
                    │    FreqUI     │
                    └───────┬───────┘
                            │
                    REST / WebSocket
                            │
                    ┌───────▼───────┐
                    │   API Server  │
                    └───────┬───────┘
                            │
                         RPC
                            │
                    ┌───────▼───────┐
                    │ FreqtradeBot  │
                    └───────────────┘
```

## 15.1 REST API 是同步控制面

例如：

```text
GET  /api/v1/ping
GET  /api/v1/status
GET  /api/v1/trades
POST /api/v1/start
POST /api/v1/stop
```

实际 endpoint 会随着版本变化，所以生产环境不要把这张表当永远不变的 API 合同，应以你当前版本 OpenAPI / 官方文档为准。 [REST API 文档](https://docs.freqtrade.io/en/latest/rest-api/)

## 15.2 WebSocket 是实时更新通道

UI 不应该不停轮询所有页面：

```text
every 100 ms -> GET everything
```

更合理的是：

```text
REST
  ↓
初始状态

WebSocket
  ↓
增量 / 实时事件
```

这也是为什么 UI 能实时显示订单、Trade、状态变化。

## 15.3 RPC 的意义

RPC 其实是一个非常重要的“内部消息接口”。

它把：

```text
核心交易引擎
```

和：

```text
Telegram
REST
Webhook
FreqUI
```

解耦。

所以如果以后你想做自己的管理前端，不一定要改 Bot 核心。

# 16. Backtesting 与 Live：为什么相同 Strategy 可能得到不同结果

这是长期使用 Freqtrade 时必须吃透的一章。

当前 `optimize/backtesting.py` 自身是独立的回测引擎，使用历史数据、DataProvider 和专用 Trade/LocalTrade 逻辑。 [Backtesting 源码](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/optimize/backtesting.py)

## 16.1 Backtest 的世界

```text
Historical candles
      ↓
Strategy analysis
      ↓
Historical execution model
      ↓
LocalTrade
      ↓
Metrics
```

## 16.2 Live 的世界

```text
Live exchange
      ↓
Current candles
      ↓
Orderbook / ticker / balance
      ↓
Strategy
      ↓
Risk checks
      ↓
Exchange order
      ↓
Fill / partial fill / reject / timeout
      ↓
Trade + Order DB
```

## 16.3 最重要的差异

### 1. Fill certainty

回测中你可能认为：

```text
“这一根 K 线的 high 到了我的 limit price。”
```

真实世界还要考虑：

```text
我排在订单簿什么位置？
有没有成交？
成交了多少？
当时 spread 如何？
交易所是否拒单？
```

### 2. 同一根 candle 内的顺序

OHLCV 只告诉你：

```text
open
high
low
close
```

并不天然告诉你：

```text
先 high 后 low
```

还是：

```text
先 low 后 high
```

所以任何依赖 intrabar 路径的逻辑都必须非常谨慎。

### 3. 余额动态

Backtest：

```text
本地计算余额变化
```

Live：

```text
交易所真实余额
+ 手续费
+ 未结算
+ 其他仓位
+ 交易所行为
```

### 4. 网络与时序

Live 是一个分布式系统：

```text
bot
exchange
internet
UI
DB
```

任何两个组件之间都有延迟。

# 17. Hyperopt：它真正改变了什么

很多人把 Hyperopt 想成：

```text
“Freqtrade 帮我自动找最好的参数。”
```

从工程角度更准确的说法是：

> Hyperopt 是对 Strategy 参数空间进行大量重复历史评估的搜索系统。

它实际上是在做：

```text
parameter candidate
        ↓
strategy instantiated / parameter applied
        ↓
backtest evaluation
        ↓
loss function
        ↓
search algorithm
        ↓
next candidate
```

## 17.1 为什么 Hyperopt 会把策略优化坏

假设你有：

```text
EMA fast: 5 ~ 50
EMA slow: 30 ~ 200
ATR period: 7 ~ 30
RSI threshold: 20 ~ 80
```

组合空间已经迅速膨胀。

如果再加：

- ROI
- stoploss
- trailing
- entry gates
- exit gates
- protection

你优化的其实不是“一个交易策略”，而是一个巨大的参数函数。

## 17.2 真正应该优化的是“结构”，不是所有数

正确顺序更接近：

```text
先确定逻辑结构
    ↓
再确定哪些参数有经济意义
    ↓
限制参数空间
    ↓
回测
    ↓
样本外验证
    ↓
Walk-forward
```

而不是：

```text
先把 30 个参数全部交给 Hyperopt
```

# 18. 多时间周期：从 decorator 到最终 DataFrame

## 18.1 多周期的正确抽象

假设：

```text
主周期 = 5m
过滤周期 = 1h
结构周期 = 4h
```

你真正需要的是一个：

```text
5m execution dataframe
+
1h context dataframe
+
4h context dataframe
```

最后在 5m frame 上形成：

```text
close_5m
ema_5m
atr_5m
trend_1h
atr_1h
regime_4h
```

## 18.2 为什么不能直接 `merge` 两个 DataFrame

因为：

```text
5m timestamps
1h timestamps
```

不在同一个时间网格上。

错误思路：

```python
merged = dataframe.merge(informative, on="date")
```

这通常会造成大量 NaN 或错误的时间对应。

Freqtrade 提供 informative helpers 与 merge 逻辑，就是为了建立“当前主周期 candle 只能看到历史上已经完成的更高周期信息”的时间因果关系。

## 18.3 一个安全的思维模型

对于 5m candle：

```text
2026-08-20 10:35
```

如果 1h candle：

```text
10:00 - 11:00
```

仍未完成，那么你不能使用 10:35 时刻的：

```text
1h close = 这个未来小时的最终 close
```

否则就是 lookahead。

真正安全的模型是：

```text
5m candle
  ↓
只能看到已经关闭的 1h candle
```

## 18.4 `@informative` 与手工 DataProvider 的区别

### `@informative`

适合：

```text
声明性
固定 timeframe
自动合并
```

### DataProvider

适合：

```text
动态读取
条件读取
实时 callback
自定义 runtime data
```

不要为了“高级”而全部改成 DataProvider；也不要因为 decorator 方便而把所有逻辑都写成 informative。

# 19. Producer / Consumer：如何把计算层与执行层解耦

当策略逐渐复杂，你会遇到一个问题：

```text
每个 bot
  ×
每个 pair
  ×
每个 timeframe
  ×
每次循环
```

重复计算大量相同信息。

这时 Producer / Consumer 思维非常有价值。

## 19.1 传统结构

```text
Bot A -> calculate
Bot B -> calculate
Bot C -> calculate
```

如果三者都需要：

```text
BTC 5m
BTC 1h
ETH 5m
ETH 1h
```

就会产生重复计算。

## 19.2 解耦结构

```text
                ┌──────────────┐
                │   Producer   │
                │ data/features│
                └──────┬───────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Bot A         Bot B        Bot C
       strategy      strategy     strategy
```

这实际上接近：

```text
计算层
---
Market data
Feature engineering
Regime classification
ML inference

执行层
---
Risk
Stake
Orders
Persistence
UI
```

## 19.3 什么时候值得这样做

当以下情况出现时：

- 多 bot 使用相同高周期指标
- ML inference 成本很高
- 大量 pair 重复生成相同 feature
- 需要统一 market regime
- 希望策略只消费 feature 而不负责计算

就应该认真考虑 Producer / Consumer 或外部 feature service。

# 20. 配置覆盖、Resolver 与运行时注入

Freqtrade 的配置系统不要理解成简单的：

```text
config.json -> dict
```

更合理的是：

```text
defaults
   ↓
config file
   ↓
strategy / exchange config
   ↓
CLI overrides
   ↓
validation
   ↓
normalized config
   ↓
runtime objects
```

## 20.1 为什么同一个字段看起来“没生效”

最常见原因是：

```text
你改了某一层
但另一层覆盖了它
```

例如：

```text
默认值
< config.json
< CLI 参数
```

因此 Debug 配置时，不要只打开 config.json。

这是非常适合你以后扩展框架的设计。

# 21. 异常、重试、恢复与故障边界

实盘最大的区别之一是：

> 错误不是异常情况，而是正常运行的一部分。

你必须考虑：

```text
网络断开
交易所超时
HTTP 429
交易所返回错误
订单状态未知
WS 断开
DB 暂时锁住
API server down
Strategy callback exception
```

## 21.1 不要看到 Exception 就认为程序应该退出

交易系统需要区分：

```text
Retryable
Temporary
Fatal
Configuration
Data corruption
```

例如：

```text
网络超时
```

通常更像：

```text
retry
```

而：

```text
Strategy class 无法加载
```

更像：

```text
fatal startup error
```

## 21.2 一个重要工程边界

```text
Bot
 ├── 可恢复异常
 ├── 可重试异常
 └── 不可恢复异常
```

如果你以后改源码，千万不要粗暴地：

```python
except Exception:
    pass
```

这样会把真实交易错误变成“静默失败”。

# 22. 数据库、缓存与持久化边界

理解三种状态：

```text
1. DataFrame / in-memory analysis
2. cache
3. persistent DB
```

## 22.1 DataFrame

它主要是：

```text
分析状态
```

可以随时重新计算。

## 22.2 Cache

它主要是：

```text
性能优化
```

可以在合理情况下丢失并重建。

## 22.3 DB

它主要是：

```text
业务状态
```

例如：

```text
Trade
Order
Pair lock
custom data
```

它不能简单地当 cache。

## 22.4 这三个概念如果混淆会产生什么问题

例如你把：

```python
self.some_runtime_state = {}
```

当作交易状态。

bot 一重启：

```text
state = {}
```

而数据库里可能还有：

```text
Trade open
```

于是运行时逻辑就会不一致。

### 原则

> **任何重启后必须保留的状态，都不应该只存在于 Strategy 实例内存里。**

# 23. 性能：到底应该优化哪里

Freqtrade 性能优化，最容易犯的错误是“优化错地方”。

## 23.1 第一优先级：减少 DataFrame 重算

例如：

```python
for pair in pairs:
    for timeframe in timeframes:
        for window in windows:
            calculate_heavy_indicator()
```

这是危险模式。

应尽量：

```text
一次计算
↓
缓存
↓
多个策略复用
```

## 23.2 第二优先级：控制 informative explosion

如果你有：

```text
20 pairs
× 4 timeframes
× 5000 candles
× 30 indicators
```

内存会快速增长。

## 23.3 第三优先级：避免 callback 里做重任务

例如不要在：

```python
custom_exit()
```

里面：

```python
requests.get(...)
```

或者：

```python
model.predict(very_large_dataframe)
```

更不要同时：

```text
每秒 × 每 pair × 每 trade
```

## 23.4 第四优先级：SQL 查询

如果 Strategy 每个循环都执行复杂数据库查询，性能会越来越差。

更好的方式：

```text
precompute
cache
batch query
```

# 24. 策略工程：如何避免 Strategy 变成“几千行神谕代码”

如果你长期使用 Freqtrade，建议不要把所有东西都塞进：

```text
MyStrategy.py
```

一个成熟项目应该逐渐变成：

```text
user_data/
├── strategies/
│   ├── TrendBreakoutStrategy.py
│   ├── MeanReversionStrategy.py
│   └── RegimeAwareStrategy.py
│
├── strategy_lib/
│   ├── features.py
│   ├── regime.py

│   ├── execution.py
│   ├── timeframes.py
│   └── utils.py
│
├── hyperopts/
└── configs/
```

## 24.1 Strategy 的合理职责

Strategy 最好专注于：

```text
feature selection
entry decision
exit decision
risk intent

```

而：

```text
市场结构计算
统计工具
通用风险函数
```

可以外置。

## 24.2 为什么这样做

因为你以后可能有：

```text
Strategy A

```

它们都需要：

```text

market regime
volatility bucket
session filter
```

那就不应该复制三份。

# 25. 源码 Debug 方法论

这是本卷最重要的部分之一。

## 25.1 不要“猜”，要建立证据链

遇到问题：

```text
为什么没有开仓？
```

错误方式：

```text
“可能是 RSI 不对。”
```

正确方式：

```text
1. Strategy 是否加载？
2. DataFrame 有没有 enter_long？
3. 当前 pair 是否在 whitelist？
4. 是否被 lock？
5. Protection 是否阻断？
6. max_open_trades 是否达到？
7. stake 是否足够？
8. confirm_trade_entry 是否返回 False？
9. Exchange 是否拒单？
10. Order 是否创建？
```

这就是调用链思维。

## 25.2 Debug 的“十层法”

```text
Layer 1  = source code loaded?
Layer 2  = strategy object initialized?
Layer 3  = dataframe present?
Layer 4  = signal present?
Layer 5  = pair allowed?
Layer 6  = risk allowed?
Layer 7  = stake allowed?
Layer 8  = order submitted?
Layer 9  = order filled?
Layer 10 = trade persisted?
```

只要你沿这十层排查，绝大部分“莫名其妙不交易”都能定位。

```text

```

### UI/API

```text

```

三者联合比单独看任何一个都可靠。

# 27. 实战：如何自己实现一个轻量级自定义风控层

假设你想增加一个非常实用的规则：

> “当策略当天累计已实现亏损超过账户权益的 2% 时，不允许新增交易。”

第一反应不要直接在 `populate_entry_trend` 写：

```python
if daily_loss > limit:
    dataframe["enter_long"] = 0
```

因为这属于：

```text
account-level runtime risk
```

而不是：

```text
candle-level signal
```

## 27.1 为什么不应该放在 populate

因为 `populate_*` 的天然输入是：

```text
DataFrame
```

但你的风控需要：

```text
Trade history
Wallet
Realized PnL
Current date
```

这是完全不同的数据域。

## 27.2 更合理的思路

可以设计：

```text
bot_loop_start
      ↓
更新账户级风控状态
      ↓
self.account_risk_state
      ↓
confirm_trade_entry
      ↓
允许 / 拒绝
```

示意：

```python
class MyStrategy(IStrategy):
    account_risk_blocked = False

    def bot_loop_start(self, current_time, **kwargs):
        """Update account-level guard once per bot loop."""
        daily_loss = self.calculate_daily_loss()
        equity = self.get_equity()
        self.account_risk_blocked = (
            equity > 0 and daily_loss <= -0.02 * equity
        )

    def confirm_trade_entry(
        self,
        pair,
        order_type,
        amount,
        rate,
        time_in_force,
        current_time,
        entry_tag,
        side,
        **kwargs,
    ):
        if self.account_risk_blocked:
            return False
        return True
```

注意：这只是架构示意，不应直接用于生产，因为你仍然需要严格定义：

- “daily loss”从什么时区计算
- 是否包含手续费
- 是否包含未实现盈亏
- 多 strategy 是否共享这个限制
- 重启后状态如何恢复
- 数据源失败怎么办

## 27.3 更进一步：Strategy 内的账户级风险与 Protection 的边界

如果你以后需要：

```text
全 bot
级别
跨 strategy
跨 pair
```

那么把逻辑全塞进某一个 Strategy 就不合理。

这时更应该研究：

```text
ProtectionManager
```

甚至考虑外部 risk service。

# 28. 实战：如何为策略增加共享状态而不污染 DataFrame

错误：

```python
dataframe["global_drawdown"] = current_global_drawdown
```

因为你正在把：

```text
account-level state
```

硬塞进：

```text
candle-level table
```

这会造成语义污染。

更合理：

```python
self.runtime_state = {
    "global_drawdown": 0.013,
    "regime": "trend",
    "risk_blocked": False,
}
```

然后：

```text
populate_*  -> candle features
callbacks   -> runtime decisions
runtime_state -> account / bot state
DB          -> persistent state
```

这是一个非常重要的分层。

# 29. 实战：如何设计多策略统一运行环境

假设你以后希望同时跑：

```text
StrategyTrend
StrategyBreakout
StrategyMeanReversion
StrategyVolatility
```

不要把它们全部塞进一个 Strategy，用：

```text
if mode == "trend":
    ...
else if mode == "breakout":
    ...
```

这种“超级 Strategy”很容易失控。

更好的方式是：

```text
                    FreqUI
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
       Bot A         Bot B         Bot C
       Trend         Breakout      MeanRev
         │             │             │
         └─────────────┼─────────────┘
                       ▼
                Shared data layer
```

每个 bot：

- 独立 config
- 独立 DB
- 独立 API port
- 独立 Strategy
- 独立日志

然后通过统一的 FreqUI 管理多个 bot 实例（具体支持方式以当前 FreqUI 版本为准）。

## 29.1 为什么数据库必须隔离

两个 bot 同时写一个 Trade database，容易把：

```text
strategy identity
trade state
API control
```

混成一个状态空间。

更可靠的是：

```text
bot-a.sqlite
bot-b.sqlite
bot-c.sqlite
```

## 29.2 为什么 API port 必须隔离

假设：

```text
Bot A -> 8080
Bot B -> 8081
Bot C -> 8082
```

统一 FreqUI 或上层 dashboard 才有机会分别访问。

# 31. Markdown 代码块规范与本手册的书写约定

# 34. 最终的“无黑盒”思维模型

当你以后研究任何一个 Freqtrade 功能时，不要问：

> “这个 API 怎么用？”

而应该问：

```text
1. 这个功能属于哪一层？
2. 谁创建它？
3. 谁持有它？
4. 谁调用它？
5. 输入是什么？
6. 输出是什么？
7. 状态保存在哪里？
8. 是否依赖时间？
9. 是否依赖交易所？
10. 是否会产生副作用？
11. 是否会进入数据库？
12. 是否会触发 RPC/UI？
13. 回测模式是否走同样路径？
14. 重启后它还存在吗？
15. 异常发生时谁负责恢复？
```

只要用这 15 个问题追一个组件，黑盒就会逐渐变成白盒。
